# Architecture

## Modules (`src/`)
| Module | Responsibility | May import |
|---|---|---|
| `core` | fixed-step loop, input, math, config, shared view types | — |
| `ships` | ship specs (data), procedural factory, GLB ships (`assets`, `glbShip`), LOD selection (`lod`), walkable deck (`deck`), sail trim, battle condition | `core` |
| `world` | wind, polar diagram, sea (waves, sea state), archipelago terrain (height function), ports, nations (flags) | `core` |
| `render` | three.js scene, camera, ocean (clip-map mesh, quality presets), shared environment, render pipeline, shadows, GI, sky, scenery, effects, other ships (`fleet`), animated crew (`crew`) | `core`, `ships`, `world` |
| `gameplay` | combat (ballistics with drag and wind), ship collisions (`collision`, `crashes`), trade and shipyard (`harbour`, `shipyard`), captain progression and boarding, game state and saving (`state`, `save`), quests (later), deck crew (`crew`), NPC patrols (`npcShips`) | `core`, `ships`, `world` |
| `settings` | player options (graphics, audio, game, debug): schema, presets, store with saved JSON | `core` |
| `audio` | procedural sound (Web Audio), spatial mix | `core` |
| `ui` | DOM HUD, map, port panel, menus | `core`, `gameplay`, `world` (static map data only) |
| `app` | composition layer: one `Mode` per screen (gallery, sailing) wiring modules together | all |
| `main.ts` | entry: owns the active `Mode`, drives the loop | `app`, `core` |

Rules: one-way dependencies; import via each module's `index.ts` (the `app` layer is the exception: it is a set of screens, not a feature module, so `main.ts` imports `app/*Mode.ts` files directly and eslint does not restrict `src/app`). `ui` currently imports `core` types and static `world` data (map, harbour panel); its `gameplay` allowance is unused for now; `render` reads state only; data tables live apart from behaviour.

## Data flow
input → gameplay state (fixed update) → render reads the latest state each frame (no interpolation yet; the loop passes `alpha` but modes ignore it, so motion can judder above 60 Hz).

## How render reads state without importing gameplay
`core/views.ts` owns the read-only snapshot types `GameView`, `ShipView`, `EnemyView`, `BallView`, `Condition`, `HitZone`, `GameEvent`, `PortView`, `WindView`, `WeatherView`, `TuningView` and the plain `Controls` input. `gameplay` produces a `GameView`; the active `app` mode passes it to `render` and `ui` each frame. So `render` and `ui` depend only on `core` types, never on `gameplay` internals. Static world data (terrain height, islands, ports) is not state: `render` and `ui` read it straight from `world`, and `gameplay` uses the same `terrainHeight` for collisions, so what you see is what you hit.

Boarding, plunder, crew, levels, trade, hiring and the shipyard (ship swap, paid repair) exist (5b–5d) and a run can be saved and continued (5f); no quests yet. See `ROADMAP.md`.

Conventions worth knowing: the sea surface is one definition (`world/sea.ts`: Gerstner waves, sea state) used by the vertex shader (`render/waves.ts` generates its GLSL), the CPU (ships ride the waves) and the game (`GameView.seaState`); see `SEA.md`; the land is one height function (`world/islands.ts`) used by the terrain meshes, the sea-shader depth texture, the map, and ship collisions; game time is fixed-step, wind is a pure function of time (`world/wind.ts`).

## Blender models, LOD and crew (phase 2c)
- `main.ts` preloads the crew GLBs (`loadCrewAssets`) before the first mode; ship GLBs load **lazily** (`requestShipAsset`, called by `createShip`; `loadShipAssets(ids)` can preload); failures only log and fall back to procedural ships / an empty deck.
- `createShip(spec)` returns a GLB-backed `Ship` when one is loaded; otherwise the procedural ship inside an upgrading wrapper (`ships/lazyShip.ts`) that swaps the GLB in under the same `root` once it has loaded. `Ship.setLod?` exists only on those; **the player's ship is never switched**.
- `GameView` now carries `others: OtherShipView[]` (NPC patrols from `gameplay/npcShips`, placed by `placePatrols` on open water around the player's start) and `crew: CrewView[]` (from `gameplay/crew`, ship-local, deterministic on the fixed step). `render` reads them like the rest of the view.
- `render/fleet.ts` places other ships (shared `render/ride.ts` wave riding) and switches their LOD by camera distance with hysteresis (`ships/lod.ts`). `render/crew.ts` clones the crew GLBs, tints materials, runs the `AnimationMixer` with a local `THREE.Clock` (so `Mode.render` is unchanged) and parents the sailors to the player ship.
- Walkable deck and obstacles come from `<id>.meta.json` through `ships/deck.ts` (`Deck`), used by gameplay crew AI.
- Debug: `?perf` (window.__perf) and `?lod=0|1|2`.


## Sea (see `SEA.md`)
- `world/sea.ts` is the one definition of the waves (Gerstner) and the sea state; `gameplay/buoyancy.ts` turns it into ship motion (`Body` springs on the fixed step) and handling effects (`seaEffects`, optional `sea` argument of `stepPlayerShip`; the duel simulator passes none), exposed to `render` through `GameView.seaState` and `ShipView/EnemyView.heave|pitch|waveRoll` (`core/views.ts`). `render` only draws: clip-map sea mesh, shaders generated from the same wave table, the foam/ripple wake map (`wake.ts`, half-float render targets) and the day's look per sea state.
- Time and weather: `world/clock.ts` (the hour, the sun and moon) and `world/weather.ts` (the weather and its overrides) are pure functions of game time; `Game.setClock` / `Game.setWeather` change them, `GameView.hour` / `weather` carry them, `render/environment.ts` paints them (`seaLook.ts`: the look for an hour and a sea state), `audio/music.ts` plays to them. Gameplay is unaffected by the hour and by default weather (see `GAME_DESIGN.md`).
- Quality and options: everything the player can change is in `settings` (see `SETTINGS.md`): the menu (gear, Esc), presets, `?quality=`, `K`, the automatic water step-down; `render/pipeline.ts` is the frame's way to the screen (MSAA/FXAA, bloom, tone mapping, AO, bounce light), `render/environment.ts` the sea, sky, fog and lights both views share. Debugging: the frame profiler overlay (F3), `?perf` (`window.__perf`), `?sea=0…1`, `game.dev.setSea`.

## Game state (5b–5f groundwork)
`gameplay/state.ts` defines `GameState`: plain serializable data (ship id and condition, captain gold/xp/kills, crew count, hold, pose and docking, discoveries, market pressure, game time). `createGame(init)` takes a `ShipSpec` (a new run, `newGameState`) or a `GameState` (resume); `Game.state()` returns a deep copy for saving. Transient things (enemies, balls, reload timers, patrols) are not in it. `GameView` carries `captain`, `cargo`, `company` (the ship's company; `crew` stays the sailors on deck) and `ShipView.specId/name/reloadSeconds`; `kills` in the view is this run's count (it drives how many enemies attack), `captain.kills` the career total. The captain's side lives in `progression.ts` (levels), `company.ts` (crew, reload, casualties), `boarding.ts` (odds, fight, loot), `plunder.ts` (who can be boarded, experience, `board`) and `desk.ts` (the game's handle on them); `world/goods.ts` lists the trade goods. `gameplay/harbour.ts` runs the port commands (`PortCommand` in `core/views.ts`: buy, sell, hire, discharge, buyShip, repair; `Game.command`) and builds `GameView.port` while moored; `world/economy.ts` holds the port tables and `TRADE`. `gameplay/shipyard.ts` adds the yard's rules (`buyShip`, `repair` commands handled by `Game.command` through `runYard`; the game's internal `equip` swaps the ship and rebuilds what hangs on it) and `ShipyardView` in `GameView.port`; `sailingMode` swaps the model when `ShipView.specId` changes. The port panel (`ui/portPanel.ts`, tabs in `portMarket.ts`, `portYard.ts`, `portTavern.ts`) gets `onCommand` from `sailingMode`, so `ui` never imports `gameplay`. Tunables that used to sit in `game.ts` live in `gameplay/tuning.ts`.

## Saving (5f)
`gameplay/save.ts`: six slots in `localStorage` (`SLOTS`: the autosave `ship-rpg.save`, which is also where the first versions wrote their one save, and five of the player's own, `ship-rpg.save.1` … `.5`; `SaveStore.load/save/clear(slot)`, `slots()`, `latest()` = the newest of all, which the gallery's "Devam et" continues), each a a JSON `{ version, savedAt, state }` where `state` is the `GameState` above. `parseSave` reads it: bad JSON, a missing or unknown version or a file from a newer game is refused (never guessed at), older versions are brought up by `MIGRATIONS` (a table of pure steps `n → n+1`, run in order on the raw JSON), then `sanitizeState` makes the result valid whatever was in the file: numbers clamped to what the ship can have, the hold trimmed to its capacity, the crew to its company, unknown goods, ports, islands and market lines dropped, an unknown ship refused. A blocked or full `localStorage` just means nothing is saved (`createSaveStore(null)` or one that throws). `savedAt` comes from the caller: game logic never reads the wall clock. To add state: add the field to `GameState` and `newGameState`, give `sanitizeState` a default for a file without it, and bump `SAVE_VERSION` with a migration only when old values must be converted (version 2 added the fleet, with a migration; 5e's reputation and quests will be version 3). `app/saves.ts` binds the store to the browser; `main.ts` passes the saved state into `startSailingMode` (the sailing mode accepts a spec or a state), the gallery shows "Devam et" when a save exists, and the settings menu has a "Kayıt" tab (`ui/saveTab.ts`: a row per slot with Kaydet and Yükle; the autosave only loads). No save is taken while an enemy afloat (not surrendered) is within 700 m (`app/saves.ts` `whyNoSave`; the autosave tries again 5 s later, mooring is always safe). What is at sea (enemies, shots) is still not saved: after a load the first enemy is spawned afresh, away from the player. The game saves itself when the ship moors and every 60 s of game time at sea (not while sunk); starting a new run from the gallery overwrites the slot at its first autosave.
